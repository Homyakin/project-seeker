# Шаг 11. Безопасное обновление данных и жизненный цикл добычи

[← К поэтапному плану](raid-redesign-plan.md) · [Новый каталог](raid-redesign-step-10-catalog-and-display-implementation.md) · [Развитие предметов](raid-redesign-step-8-implementation.md)

Дата завершения: 2026-09-18.

## Итог

Выпуск `SCALING_V1` теперь записывается в общую базу неделимой операцией, но не открывается целиком. Сорок прежних кодов предметов и одиннадцать прежних кодов модификаторов остаются доступными для новых выдач; двадцать два новых предмета и четыре новых модификатора записываются выключенными. Само наличие строки в таблице больше не означает возможность получить её случайно или купить напрямую.

Уже выданный экземпляр продолжает ссылаться на прежний идентификатор строки, сохраняет владельца, состояние экипировки, редкость, модификатор и уровень усиления. Его характеристики пересчитываются от новой основы того же кода и того же уровня. Историческое назначение модификатора читается без повторной проверки по новым правилам назначения.

Полный выпуск пока не включён. Переход в действующее состояние реализован и сохраняется в БД, но рабочий запуск его не вызывает: это остаётся частью общей боевой приёмки шага 12.

## Состояние выпуска и признаки доступности

В схему добавлены два независимых признака:

- `item_object.acquisition_enabled` — разрешено ли создавать новый экземпляр этой основы;
- `item_modifier.assignment_enabled` — разрешено ли назначать модификатор новому экземпляру.

Существующие строки при изменении схемы получают значение `true`, после чего значение по умолчанию меняется на `false`. Поэтому забытый будущий запрос вставки не открывает новую добычу сам по себе. Запись каталога всегда передаёт требуемое значение явно.

Состояние выпуска хранится в `item_catalog_release`:

- `STAGED` — определения записаны, но действующим остаётся исходный набор `40/11`;
- `ACTIVE` — принят полный набор `62/15`.

Первая подготовка одновременно записывает все определения, выключает всё вне исходного набора и сохраняет `STAGED`. Повторный запуск обновляет определения, но не переписывает признаки доступности. Поэтому последующее включение выпуска и будущий ручной вывод отдельного предмета не отменяются перезапуском приложения.

Переход `STAGED → ACTIVE` выполняется один раз. Он включает ровно коды принятого выпуска. Повторный вызов ничего не меняет, поэтому позднее выведенные из добычи строки не включаются обратно.

## Пути выдачи и историческое чтение

Фильтр доступности поставлен на границе каждого рабочего пути создания нового экземпляра:

- случайный выбор основы предмета;
- случайный выбор модификатора;
- список основ для прямой покупки;
- повторная проверка основы по идентификатору при покупке;
- общий способ выдать уже выбранную основу.

Последний способ не доверяет переданному объекту: он повторно читает строку из БД по идентификатору и отвергает выдачу, если она уже выключена. Выбор основы и модификатора удерживает разделяемую блокировку строки до завершения операции выдачи, поэтому одновременное выключение дожидается уже начатой операции. Покупки и повышение редкости дополнительно последовательно выполняются для одного персонажа, а изменяемый предмет при повышении редкости блокируется до записи. Старые способы массовой записи, которые неявно включали новую строку, удалены.

Обычное чтение по идентификатору намеренно не фильтруется. Благодаря этому экипированные предметы, предметы в сумке и сохранённые модификаторы продолжают открываться после вывода их основы или сочетания из нового отбора. В частности, все 60 исторических сочетаний, которые больше не проходят новое правило назначения, остаются читаемыми и боеспособными.

Справка о ячейках одиннадцати доступных умений теперь берёт их новые определения из `SCALING_V1`, но отбирает только действующие прежние коды. Поэтому показ не расходится с фактическим новым назначением, а четыре ещё выключенных умения до шага 12 в справку не попадают.

## Вероятность доспехов

Запрос случайной основы сначала оставляет только строки с `acquisition_enabled = true`, а затем равномерно выбирает одну строку. После включения полного выпуска в каждой неоружейной ячейке находятся ровно восемь одноячеечных доспехов:

- вероятность каждого отдельного предмета равна `1/8`;
- каждого типа защиты представлено ровно два;
- суммарная вероятность каждого типа защиты равна `2/8 = 1/4`.

До шага 12 действуют четыре прежних доспеха на ячейку — по одному каждого типа. Двадцать новых доспехов присутствуют в БД, но не участвуют ни в случайном выборе, ни в прямой покупке.

## Политика уже усиленных предметов

Принята ретроактивная политика без отдельной выплаты:

1. код объекта и уровень `n` сохраняются;
2. прежняя пятипроцентная траектория больше не закрепляется за экземпляром;
3. состояние считается как `B₁(bновое,n)` от новой основы того же кода;
4. редкость, модификатор, владелец и экипировка не меняются;
5. уровень не умножается и не переносится в другой номер;
6. осколки автоматически не начисляются.

Уровень трактуется как сохранённая мера уже выполненного усиления, а не как право на прежнее абсолютное число характеристики. Это согласуется с ранее принятым разрешением менять основы существующих предметов. Значительные ослабления не скрыты: они должны пройти боевую приёмку шага 12; справочная мощь не используется для их оправдания.

Сравнение 40 прежних кодов на контрольных уровнях показывает количество улучшенных / равных / ослабленных предметов только среди предметов, у которых соответствующий канал существует:

| Уровень | Здоровье, из 24 | Атака, из 16 | Защита, из 24 |
|---:|---:|---:|---:|
| `+0` | 22 / 1 / 1 | 14 / 0 / 2 | 24 / 0 / 0 |
| `+3` | 20 / 0 / 4 | 13 / 0 / 3 | 24 / 0 / 0 |
| `+6` | 19 / 0 / 5 | 9 / 0 / 7 | 24 / 0 / 0 |
| `+10` | 11 / 5 / 8 | 5 / 0 / 11 | 24 / 0 / 0 |
| `+20` | 1 / 7 / 16 | 5 / 0 / 11 | 24 / 0 / 0 |
| `+75` | 0 / 0 / 24 | 5 / 0 / 11 | 24 / 0 / 0 |

Два крайних примера на `+20`: здоровье нагрудника снижается с 1200 до 800, а видимая атака алебарды — с 796 до 480. На предельном поддерживаемом состоянии `+75` эти значения меняются с 2850 до 1350 и с 1891 до 810 соответственно. Одновременно прежний кинжал с основой атаки 42 остаётся читаемым: на `+1` прежняя формула даёт 44, а новая основа и `V1` дают 122. Автоматическая проверка проходит все сорок кодов на каждом уровне `+0…+75`, а чистые проверки формулы отдельно покрывают переполнение.

При изменении любого игрового поля основы ревизия всех связанных экземпляров увеличивается один раз. Поэтому подтверждение усиления, показанное до обновления каталога, становится устаревшим до списания осколков. Повторная подготовка того же выпуска ревизию не меняет.

Исход усиления с откатом уровня считает состояние `n−1` заново от основы. На настоящей строке PostgreSQL проверен переход меча `+6 → +5`: атака меняется с 396 на 390, уровень и ревизия читаются повторно из БД.

## Откат выпуска

Миграция схемы сразу, до запуска прикладного кода, сохраняет снимок прежних определений предметов и модификаторов. Поэтому откат возможен даже после ошибки запуска между применением миграции и подготовкой выпуска.

На новой пустой базе миграции ещё нечего копировать. В этом случае первая подготовка в той же операции сначала записывает неизменяемые прежние определения `40/11`, проверяет число строк, сохраняет их как исходную точку отката и только затем накладывает `SCALING_V1`. Частично заполненное состояние без полного исходного снимка считается ошибкой и останавливает подготовку: оно не принимается за достоверную исходную версию.

Безопасный откат выполняет следующие действия в одной операции:

1. проверяет наличие всех строк исходного снимка;
2. запрещает откат, если хотя бы один предмет ссылается на строку, добавленную после снимка;
3. ещё раз увеличивает ревизию экземпляров, чьи игровые определения возвращаются назад;
4. восстанавливает все поля прежних 40 предметов и 11 модификаторов;
5. удаляет только строки, отсутствовавшие в снимке;
6. удаляет признаки доступности, состояние выпуска и служебный снимок.

Первая проверка создаёт экземпляр нового предмета с новым модификатором и подтверждает, что откат отказан без частичных изменений. После удаления этого проверочного экземпляра тот же откат успешно возвращает прежние определения, сохраняет три старых экземпляра и их уровни, повторно меняет ревизии и удаляет служебную схему. Вторая проверка начинает с полностью пустого каталога, создаёт исходную точку `40/11`, выдаёт прежний предмет и подтверждает успешный возврат его определения и уровня.

Уменьшать ревизию при откате нельзя: это могло бы снова сделать действительным подтверждение, показанное для другой формулы.

## Проверка на PostgreSQL

Два интеграционных сценария выполнены на отдельных схемах настоящего PostgreSQL. Оба применяют первые 123 изменения схемы, а затем изменение шага 11 как настоящее обновление базы. Первый заранее записывает прежний каталог и существующие строки инвентаря; второй начинает с пустого каталога.

Проверены:

- экипированный редкий меч `+6` с историческим модификатором;
- такой же предмет `+3` в сумке без модификатора;
- прежний предмет с базовой атакой меньше 60 на `+1`;
- сохранение идентификаторов, владельца, экипировки, редкости, уровня и исторического назначения;
- ровно 62 определения предметов и 15 модификаторов после подготовки;
- ровно 40 и 11 доступных строк до приёмки;
- исключение выключенных строк из ста последовательных случайных выборов каждого вида;
- отказ прямой выдачи выключенной основы;
- идемпотентная повторная подготовка;
- устойчивость включённого состояния после повторной подготовки;
- восемь доспехов и два доспеха каждого типа в каждой неоружейной ячейке после включения;
- успешный и запрещённый откат;
- создание исходной точки отката `40/11` на новой базе и успешный откат уже после выдачи прежнего предмета;
- удаление при откате обоих служебных индексов вместе с таблицами и признаками доступности.

Это воспроизводимая проверка поведения схемы и настоящих строк, но не снимок рабочей базы. Перед боевым развёртыванием остаётся обязательная только для эксплуатации сверка фактического распределения:

```sql
SELECT io.code, i.enhance_level, count(*) AS item_count
FROM item i
JOIN item_object io ON io.id = i.item_object_id
GROUP BY io.code, i.enhance_level
ORDER BY io.code, i.enhance_level;
```

Она не меняет принятую формулу, но позволяет заранее показать владельцам фактические изменения на всех уровнях, которые действительно встречаются в рабочей базе.

## Порядок развёртывания

Старый исполняемый файл не знает о признаках доступности. Поэтому обновление нельзя раскатывать одновременно со всё ещё работающими старыми экземплярами приложения: после вставки новых строк они могли бы выбрать их без фильтра.

Безопасный порядок для текущей одноэкземплярной службы:

1. остановить старое приложение;
2. сделать резервную копию БД;
3. запустить новую версию, применить миграцию и подготовить `SCALING_V1`;
4. проверить состояние `STAGED`, количества `40/11` и фактические уровни;
5. только затем открыть обработку команд.

Возврат выполняется в обратном порядке: остановить новую версию, откатить изменение БД и только после этого запускать старую. Откат одного исполняемого файла без отката БД небезопасен. Для будущего одновременного запуска нескольких экземпляров потребуется отдельное двухфазное развёртывание: сначала схема и фильтры на всех узлах, затем запись новых строк.

## Проверки и граница результата

Помимо PostgreSQL-сценария проверки закрепляют точный набор `40+22` и `11+4`, все исторические назначения, новое правило назначения, признаки доступности магазина, справку, ревизии, прежние основы меньше 60, обратимость уровня, состав доспехов и полный откат определений.

Чистая сборка игрового модуля завершена успешно: 590 проверок без ошибок, из них 21 пропущена в обычном запуске. Две условные проверки PostgreSQL отдельно выполнены на настоящей БД без пропусков; остаются 19 намеренно отключённых проверок.

На этом шаге намеренно не выполнены:

- включение 22 новых предметов и 4 новых модификаторов в рабочем запуске;
- переключение экипировки игроков на `SCALING_SKILLS_V1`;
- боевая приёмка основ и формул умений;
- выбор окончательного `Kмасш`;
- изменение походов, аномалий, наград и экономики осколков.

Следующий шаг — воспроизводимо проверить боевые роли и только после принятия перевести сохранённое состояние выпуска из `STAGED` в `ACTIVE`.
