## Правила выполнения

- Статусы: `[ ]` — не начат, `[~]` — выполняется, `[x]` — завершён, `[!]` — заблокирован.
- За одну команду выполняется ровно один пронумерованный шаг.
- Переход к следующему шагу — только по явной команде пользователя.
- Перед началом шага его статус меняется на `[~]`.
- После завершения шага в этот файл добавляются результаты, принятые решения, тесты и обнаруженные риски.
- Продуктовая спецификация сначала утверждается, а её реализация выполняется отдельным следующим шагом.
- Если результат шага меняет предпосылки более поздних шагов, сначала обновляется этот план.
- Источник истины — код, game-data и результаты симуляций, а не README.

## Зафиксированные принципы

### Порядок проектирования

1. Зафиксировать текущее состояние и сделать воспроизводимые симуляции.
2. Спроектировать боевые архетипы.
3. Определить новую stat economy и модель силы предметов.
4. Ребалансировать существующие предметы и добавить новое снаряжение.
5. Проверить архетипы в бою и заморозить эталонные сборки.
6. Только после этого проектировать и калибровать рейды относительно новых сборок.

### Difficulty и размер группы

- D1–D10 — основная содержательная прогрессия.
- Вехи рейда: D1, D5 и D10; промежуточные уровни усиливают составы и статы.
- D11+ — Ascension: числовой рост и комбинации уже известных противников и skills.
- В UI сохраняется непрерывная нумерация `D1`, `D10`, `D11` и далее; D11+ дополнительно помечаются как Ascension.
- Recommended party общий для рейдов: `R = 5`.
- Категории прохождения:
  - Expedition: 1–3 игрока;
  - Raid: 4–7;
  - Warband: 8+.
- Размер группы меняет масштаб encounter, но не открывает отдельные типы контента.
- Новый участник обычно должен немного помогать группе.
- `BattlePersonage.power()` не участвует в новой генерации рейдов.

### Выбор Difficulty и рекорд

- В настройках группы администратор заранее выбирает постоянную стратегию:
  - 🟢 `SAFE` → `max(1, record - 1)`;
  - ⚔️ `CURRENT` → `max(1, record)`;
  - 🔥 `NEW_RECORD` → `record + 1`.
- Новый общий рекорд групп начинается с D0; старые результаты и сезонные очки не удаляются.
- Стратегия по умолчанию — `CURRENT`.
- Рекорд общий для всех типов рейдов.
- Для одинакового рекордного D дополнительно сохраняется минимальный состав, тип рейда и дата достижения.

### Награды

- Base reward не уменьшается из-за размера группы.
- Expedition получает положительный challenge bonus.
- Warband не получает отрицательный multiplier, а просто не получает challenge bonus.
- Используются существующие награды: деньги, предметы и сезонные raid points.
- Новая валюта в первую версию не добавляется.

## Важные факты текущей реализации

- `ItemObject` задаёт attack, defense, HP, crit, dodge, crit multiplier, speed, threat, range и допустимые slots.
- `ItemRarity` сейчас меняет только число skill points модификатора: от 0 до 4.
- Storm enhance масштабирует только attack, defense и HP; вторичные статы не меняются.
- Каталог загружается через upsert по `ItemObject.code`. Ребаланс существующего code автоматически меняет все уже выпавшие экземпляры этого предмета.
- Удаление объекта из TOML не удаляет строку из БД и не исключает её из случайного loot pool.
- Поэтому до изменения каталога необходимо отдельно решить модель item power, совместимость существующих предметов и способ вывода предметов из loot pool.
- Текущая raid generation одновременно зависит от player `power()`, legacy raid level и group-size коэффициентов.
- Предварительный Myconid baseline показал скачки win rate между N=1/2 и около N=7/8, а также большой разрыв между random, default и counter-pick сборками.

### [x] Шаг 1. Полный аудит текущих экипировки и рейдов

Проверить по коду и данным:

### [ ] Шаг 2. Сделать воспроизводимый combat simulator

Добавить контролируемый seed для battle RNG, включая initiative start, shuffle, target selection, crit, dodge, damage variance и случайные варианты NPC. Калибровочные симуляции не должны запускаться в обычном unit-test наборе.

Симулятор должен собирать:

- win rate и доверительный интервал;
- медиану и p95 длительности;
- выживших и остаток здоровья;
- damage dealt/taken и число ходов;
- результаты по сборке, составу команды, Difficulty и размеру группы.

Для поиска параметров использовать 1 000 боёв на ячейку, для приёмки ключевых ячеек — 10 000.

**Критерий завершения:** одинаковый seed даёт одинаковый отчёт; обычный Maven build не замедляется.

### [ ] Шаг 3. Спроектировать боевые архетипы

Сначала описать игровые роли независимо от конкретных текущих предметов. Для каждого архетипа определить:

- назначение в группе;
- позицию и рабочую дальность;
- основные и вторичные статы;
- предпочтительные attack/defense types;
- threat profile;
- набор подходящих существующих skills;
- сильные стороны, слабости и counterplay;
- допустимые гибриды и запрещённые сочетания, стирающие слабости.

Стартовые кандидаты для обсуждения: Vanguard/Tank, Bruiser, Skirmisher, Marksman, Arcanist и Controller. Список не считается утверждённым до завершения шага.

Отдельно определить, требуется ли хотя бы одному архетипу новый skill/modifier. Новые mechanics добавляются только при доказанном пробеле, который нельзя закрыть текущими skills.

**Артефакт:** утверждённая archetype matrix.
**Критерий завершения:** у каждого архетипа есть различимая боевая история, преимущество и уязвимость; пользователь утвердил список.

### [ ] Шаг 4. Определить stat economy и модель item power

Для каждого slot и архетипа определить stat budget и exchange rates между:

- HP, attack и defense;
- speed;
- dodge и crit chance;
- crit multiplier;
- range;
- threat;
- modifier skill rank.

На этом шаге отдельно выбрать одну модель прогрессии предметов:

1. rarity остаётся только skill rank, а статы определяются ItemObject;
2. rarity дополнительно масштабирует статы;
3. вводится отдельный item tier/level, независимый от rarity.

Решение должно учитывать уже существующие предметы, storm enhancement и будущую Difficulty-шкалу. Баланс оценивается симуляциями, а не текущим `power()`.

**Артефакт:** таблицы Weak/Average/Good/Endgame, slot budgets, caps и ожидаемый прирост от upgrade.
**Критерий завершения:** утверждена одна модель item power и количественные диапазоны всех статов.

### [ ] Шаг 5. Спроектировать новый каталог снаряжения

Составить полную матрицу `архетип × slot × вариант`:

- какие текущие ItemObject сохраняются без изменений;
- какие получают новые статы, роль или совместимость с modifiers;
- какие новые ItemObject добавляются;
- какие предметы становятся sidegrade, upgrade или специализированным counter-pick;
- какие старые предметы перестают выпадать, но сохраняются у владельцев;
- нужны ли новые modifiers и на каких slots они доступны.

Для каждого предмета заранее определить code, slots, локализации, exact stats, attack/defense type, range и archetype tags в дизайн-таблице. Существующие codes не переименовывать без отдельной миграционной причины.

**Критерий завершения:** каталог и все числовые характеристики утверждены до изменения TOML/БД.

### [ ] Шаг 6. Реализовать новую модель предметов и каталог

Реализовать утверждённые изменения item model, если они потребовались на шаге 4. Затем обновить текущие ItemObject, добавить новые предметы и modifiers, локализации и validation tests.

На этом шаге raid generators и награды не ребалансируются.

**Критерий завершения:** каталог загружается, все slots имеют допустимые предметы/modifiers, существующие item codes разрешаются, полный Maven package проходит.

### [ ] Шаг 7. Реализовать безопасную миграцию и loot lifecycle

Проверить на PostgreSQL поведение существующих инвентарей после upsert новых статов. Если предметы выводятся из выпадения, добавить явный признак lootability/enabled и фильтрацию `getRandomObject`, не удаляя строки с внешними ключами.

Проверить:

- существующие экипированные и лежащие в сумке экземпляры;
- новые выпадения;
- modifier compatibility;
- item random pool;
- storm enhancement до и после ребаланса;
- rollback/data compatibility.

**Критерий завершения:** ни один существующий item не теряется и retired items больше не выпадают.

### [ ] Шаг 8. Проверить архетипы и заморозить raid fixtures

Прогнать mirror, counter и mixed-team матрицы для утверждённых архетипов. Проверить solo и командные составы, позиции, range, threat, redundancy и skill synergies.

Базовые критерии:

- mirror match близок к 50%;
- ожидаемый counter даёт заметное, но не гарантированное преимущество;
- нет одной сборки, доминирующей во всех matchup;
- каждый архетип сохраняет заявленную слабость;
- несколько хороших upgrades дают ощутимый прирост, но не заменяют composition.

После приёмки создать зафиксированные Weak/Medium/Strong команды для raid calibration. Любое последующее изменение их предметов требует повторного прогона raid matrix.

**Критерий завершения:** archetype balance принят пользователем, fixtures заморожены.

### [ ] Шаг 9. Спроектировать Myconid D1–D10 под новые архетипы

Подготовить точную таблицу составов, статов и skills:

- D1: базовые Guardian и Slinger;
- D2–D4: рост чисел и масштаба состава;
- D5: elite-варианты на существующих skills;
- D6–D9: рост доли elite и тяжёлые комбинации;
- D10: полная версия encounter с boss-вариантом и всей палитрой Myconid.

Encounter должен проверять несколько архетипов, но не требовать единственную обязательную сборку. Slinger должен иметь range, соответствующий BACK, без скрытого автоматического переноса вперёд.

**Критерий завершения:** полная таблица D1–D10 утверждена до написания нового генератора.

### [ ] Шаг 10. Реализовать fixed-difficulty Myconid вне production-пути

Ввести запрос генерации вида `RaidEncounterRequest(raidType, difficulty, partySize)`. Новый генератор принимает только Difficulty и размер группы — не список персонажей и не их `power()`.

Старый генератор сохранить для уже созданных событий. Ввести версии `LEGACY_POWER` и `FIXED_DIFFICULTY_V1`.

**Критерий завершения:** изменение gear при одинаковых Difficulty и N создаёт идентичный encounter; production пока использует legacy-версию.

### [ ] Шаг 11. Откалибровать group-size scaling

Подобрать enemy budget симуляциями для N=1–30. Основные контрольные размеры — 3, 7 и 15 игроков.

Целевой профиль около frontier:

- N=3: около 55% побед;
- N=7: около 60%;
- N=15: около 65%;
- допуск ±5 процентных пунктов.

Между соседними N не должно быть необъяснимых скачков более 10 пунктов. Новый типичный участник не должен снижать win rate группы.

**Критерий завершения:** budget curve и отчёт N=1–30 утверждены пользователем.

### [ ] Шаг 12. Откалибровать Ascension D11+

Использовать полную палитру D10, увеличивая числовой budget и смешивая уже известные elite/boss-комбинации. Новых типов врагов после D10 не вводить.

Кривая должна быть монотонной, не переполнять числовые типы на высоких D и не иметь игрового cap; допустим только технический overflow guard.

**Критерий завершения:** формула Ascension и симуляции D10–D30 утверждены.

### [ ] Шаг 13. Реализовать рекорд и выбор Difficulty

Добавить отдельное хранилище новой прогрессии, не переиспользуя legacy `pgroup.raid_level`, пока остальные рейды не мигрированы.

Хранить лучший общий D, минимальный состав, raid type, дату и выбранную стратегию. Добавить три admin-only кнопки в настройки группы. При создании события вычислять D из стратегии и фиксировать его в `RaidParams`.

Старые JSON events читать через version/fallback как `LEGACY_POWER`. Новый рекорд записывать только после победы; победа на том же D меньшим составом обновляет prestige-record.

**Критерий завершения:** миграция создаёт D0 без удаления истории; тесты покрывают стратегии, права и legacy compatibility.

### [ ] Шаг 14. Спроектировать reward economy относительно новой экипировки

Только после фиксации stat tiers и Difficulty подготовить точные формулы:

- base money по D;
- rarity/item-tier distribution по D1–D10;
- медленное улучшение reward profile в Ascension;
- seasonal raid points;
- Expedition challenge bonus.

Base money и базовый item chance не уменьшаются с размером группы. Pity-механика сохраняется. Warband не получает отрицательный multiplier.

**Критерий завершения:** прогноз наград для Weak/Medium/Strong, N=3/5/7/15 и D1/D5/D10/D15 утверждён.

### [ ] Шаг 15. Реализовать rewards

Разделить base и challenge расчёты. Категорию прохождения и бонус сохранять в результате события и показывать в отчёте. Exhausted-персонажи по-прежнему не получают награду.

**Критерий завершения:** тесты подтверждают отсутствие group-size penalty в base reward и корректность challenge bonus, item progression и raid points.

### [ ] Шаг 16. Переключить новые Myconid events на production-модель

Обновить локализации Difficulty, Ascension и Expedition/Raid/Warband.

**Критерий завершения:** полная simulation matrix и `mvn -f game/pom.xml clean package` проходят; в новом пути нет чтения player `power()`.

## Общие приёмочные критерии

- Архетипы и предметы утверждены до начала raid calibration.
- Новая экипировка образует sidegrades и осмысленные upgrades, а не одну лучшую комбинацию.
- При одинаковых Difficulty и N gear игроков не меняет сгенерированных NPC.
- Улучшение gear повышает win rate и доступный frontier.
- Difficulty монотонно повышает угрозу.
- Все размеры N=1–30 получают одну и ту же палитру контента соответствующего D.
- Добавление игрока обычно помогает, но большая группа не покупает много D одной численностью.
- Base reward не штрафует за друзей; малая группа получает challenge reward.
- Старые items, events и исторические отчёты остаются читаемыми после миграций.
- После каждого implementation step выполняется полный Maven package.

## Вне первого vertical slice

- Новый универсальный framework scripted encounter mechanics.
- Полный редизайн FRONT/MID/BACK.
- Новая валюта.
- Изменение world raids и anomaly, кроме последующей перекалибровки `power()`.
